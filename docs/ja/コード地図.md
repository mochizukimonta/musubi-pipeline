# コード地図

全21モジュールの役割と、「どこをいじると何が変わるか」の対応表。
コードを実際に触る人向けの詳細資料です。全体の設計思想と層構造は
[ARCHITECTURE.md](../../ARCHITECTURE.md) を先に読んでください。

対象バージョン: v0.26.0

---

## 全体アーキテクチャ(3層構造)

```
┌─ UI層 ──────────────────────────────────────┐
│ ui.py(パネル描画のみ。I/O禁止)              │
├─ オペレーター層(bpy依存)─────────────────┤
│ ops.py st_ops.py task_ops.py review_ops.py    │
│ ver_ops.py quality_ops.py spec_ops.py reel.py │
├─ データ層(bpy非依存 = Blender外でも動く)──┤
│ core.py sync.py tasks.py reviews.py           │
│ versions.py spec.py render_profiles.py        │
│ syncthing.py board_html.py                    │
│ security.py(bpyは任意参照)                  │
│ ─ 例外: quality.py は bpy.data を読む         │
│   (シーン検査のため。書き込み・UIはしない)   │
└───────────────────────────────────────────────┘
```

- **データ層は `import bpy` しない**。システムPythonから直接テスト・修理
  できるのはこのため(Blenderを起動できない状況でも同期設定を読んで
  直せる)。データ層に機能を足すときも bpy に触れないこと
- ディスク上のデータはすべて `<プロジェクト>/.musubi/` 配下のJSON。
  **「共有インデックスを持たない」が全体の設計原則**(1件=1ファイル、
  一覧はフォルダ走査)。P2P同期での書き込み競合をゼロにするため
- Blenderへのフックは2つだけ: `load_post`(開いた時)と `save_post`
  (保存した時)。**常駐タイマー・常駐スレッドは禁止**
  (クリエイターの作業を妨げないための確定方針)

## 各ファイルの概要と改造ポイント

### \_\_init\_\_.py — 登録の入口
- `bl_info`(バージョン番号はここと blender_manifest.toml の2箇所)
- `_scene_props()` に全カスタムプロパティの定義が集まっている
  (Scene = ファイルに保存される値 / WindowManager = セッション限り)
- `register()` がクラス登録・プロパティ定義・ハンドラー登録を行う

**改造ポイント**
- 新しいプロパティを足す → `_scene_props()` に追加し、`_del_scene_props()`
  の削除リストにも必ず追加。「.blendに残したい値」ならScene、
  「保存したくない一時値(コメント欄など)」ならWindowManager
- 新モジュールを作った → ここの import と、各モジュールの `CLASSES` を
  register が拾う流れに合わせる
- **注意**: register は RestrictBlend 下で走る。`bpy.data.scenes` 等に
  触るコードを register 内に書くとインストール時にクラッシュする
  (過去に実際に踏んだ)。`bpy.data` を読む必要がある初期化は、
  `bpy.app.timers` の1回きりタイマーに逃がすか、`load_post` ハンドラーで行う

### blender_manifest.toml — Extension配布定義
- バージョン・最小Blender(4.2)・ライセンス・権限宣言(files/network)
- `[build] paths_exclude_pattern` が配布zipから除外するもの。
  `tests/` と `docs/` はこのフォルダの外(リポジトリ直下)にあるため
  除外指定は不要

**改造ポイント**: リリースごとに version を上げる(\_\_init\_\_.py と同時に。
片方だけだと `tests/test_manifest.py` が赤くなる)

## データ層(bpy非依存)

### core.py — 命名規則・パス安全・プロジェクト構造の中核
- `SCENE_RE / CUT_RE / OUTPUT_RE`: scene01 / c01 / c01.001.mp4 の命名規則
- `TEMPLATES`: フォルダ構造テンプレート(film / asset / minimal)
- `safe_path()`: **全ファイル書き込みが通る門番**。ルート外へのパス
  (シンボリックリンク脱出含む)を PipelineError にする
- `atomic_replace()`: 同期ツールがファイルを掴んでいても書けるリトライ付き
  置換。**プロジェクト内への書き込みは必ずこれか safe_path 経由で**
- `detect_root()`: 開いたblendから上に辿って `.musubi` を探す(自動検出)
- `write_project_info / read_project_info`: `.musubi/project.json`(同期ID記録)

**改造ポイント**
- カット番号を4桁にしたい等、**命名規則の変更はここの正規表現**
  (ただし既存プロジェクトとの互換に注意。OUTPUT_REは tasks/reel も参照)
- フォルダテンプレートを増やす → `TEMPLATES` に1エントリ追加するだけで
  オペレーターのメニューとUIに自動で出る
- 出力の連番形式(.mp4固定)を変えたい → `OUTPUT_RE` と
  `next_output_path()`、reel.py の収集、board_html.py のリンク生成が連動

### sync.py — 整合性検証・ロック・危険ファイル検出
- `IGNORE_PATTERNS`: 照合リストの対象外(.musubi/ 等)
- `DANGEROUS_EXTENSIONS`: 監査が赤警告にする拡張子(.exe .py .html …)
- `write_manifest / verify_against`: SHA-256照合リスト(同期の担保)
- `acquire_lock / release_lock / read_lock`: アドバイザリロック
  (`cXX.blend.lock`、host_id で自他判定)
- `LOCK_STALE_HOURS`: ロックが「古い」と表示される時間(12h)

**改造ポイント**
- 監査対象の拡張子を増減 → `DANGEROUS_EXTENSIONS`(.svg が誤検知するなら
  ここから外す)
- 照合リストから除外したいファイル → `IGNORE_PATTERNS`
- ロックの持ち主判定を変えたい(ユーザー名単位にする等)→ `host_id()` と
  acquire_lock の `existing.get("host") != host_id()` 比較。
  **ただし ops.py の自動ロックも同じ前提なので同時に見直すこと**

### tasks.py — 進捗ステータスのデータ層
- `STATUSES`: 状態の定義と表示名(todo/wip/review/retake/approved/omit)
- 1カット=1ファイル `.musubi/status/sceneXX_cYY.json`
- `board()`: フォルダ走査でボードの全行を構築(ロック・最新出力も付与)
- `NOTE_MAX = 500`: 指示メモの最大長

**改造ポイント**
- **状態を追加/名前変更 → `STATUSES` に足すだけで、ボードUI・状態変更
  メニュー・HTMLボード・集計に自動反映**(色は board_html.py の
  STATUS_COLORS にも追加)
- ステータスに項目を足す(締切など)→ `_default()` にキー追加+
  `update_status()` の許可リスト `("status", "assignee", "note")` に追加。
  task_ops.py に編集オペレーター、board_html.py に表示列を足す
- 完了率の計算(omit除外など)→ `summary()`

### reviews.py — レビューコメントのデータ層
- 1コメント=1ファイル `.musubi/reviews/sceneXX_cYY/<時刻>_<端末>.json`
  (追記のみ・編集不可の設計。だから同時書き込みで絶対に衝突しない)
- `VERDICTS`: 判定の種類(comment/retake/approved)
- `COMMENT_MAX = 1000`

**改造ポイント**
- 判定を増やす(「保留」など)→ `VERDICTS` に追加+review_ops.py の
  `VERDICT_ICONS` にアイコン、ステータス連動が必要なら
  review_ops.py `MUSUBI_OT_review_add.execute` の分岐に追加
- コメント削除機能を作りたい → 設計と衝突する(不変ログが前提)。
  「取り消しコメントを追加する」方式を推奨

### versions.py — バージョン履歴のデータ層
- `.musubi/versions/<相対パス>/<日時>_<端末>.blend` + サイドカーJSON
- `snapshot()`: コピー→コピー先をハッシュ→重複排除→確定(この順序は
  レース対策なので変えない)
- `restore()`: 復元前に現状を自動スナップショット
- `prune()`(ファイル単位)/ `prune_all()`(プロジェクト横断)/
  `enforce_size_cap(max_bytes)`(合計上限で古い順削除・各ファイル最新は保護)
- `_iter_version_dirs()`: 履歴フォルダ(葉)を全列挙する走査の基盤
- `DEFAULT_KEEP = 20`: 既定の保持世代数

**改造ポイント**
- 保持世代の既定値 → `DEFAULT_KEEP`(UI側の既定は \_\_init\_\_.py の
  musubi_version_keep)
- サイズ上限の自動整理タイミング → ops.py `_snapshot_bg`(保存後に
  `enforce_size_cap` を呼ぶ。上限値はプリファレンス history_max_gb)
- 履歴の対象を絞る/広げる → `_rel_under_root()`(現在 .musubi 内は拒否)
- 世代名の形式 → `VERSION_NAME_RE` と snapshot の `stamp` 生成(両方)。
  enforce_size_cap の「最古から削除」は世代名の辞書順に依存するので
  タイムスタンプ接頭辞の形式を変えるならここも見直す
- **履歴を同期するかどうか** → syncthing.py `HISTORY_IGNORE_LINE` /
  `write_stignore(local_only_history=)` / `apply_history_ignore()`。
  プリファレンス history_local_only のトグルが端末の全共有フォルダの
  `.stignore` を書き換える(`.stignore` は端末間同期されないので端末ごと)

### spec.py / render_profiles.py — プロジェクト仕様
- spec.py: `.musubi/spec.json` の読み書き(title / render_profiles
  {final, preview} / notes)。format 2。旧形式は load 時に自動移行
- render_profiles.py: **`SETTINGS` 辞書がこの機能の本体**。
  key → (グループ, 表示名, getter(sc,vl), setter) の約22項目
  (エンジン、サンプル数、解像度、fps、出力形式、パス、Cryptomatte…)

**改造ポイント**
- **仕様書に管理項目を足す → render_profiles.py の `SETTINGS` に
  1行追加するだけ**で、取り込み・適用・差分チェックリスト・QCの
  3すくみ判定・HTMLボードの対照表すべてに自動反映される
- 既定プロファイル(新規プロジェクトの初期値)→ spec.py
  `default_profiles()`
- 注意: getter/setter は Blender 4.x/5.x 両対応にする
  (`hasattr(ims, "media_type")` パターンを踏襲)

### syncthing.py — Syncthing自動セットアップと制御(最大のファイル)
- 導入: `download_binary`(公式GitHub+SHA-256検証)、`ensure_config`、
  `start / shutdown`(`%LOCALAPPDATA%\musubi_pipeline\syncthing\`)
- 制御: `api()` がローカルREST(127.0.0.1:28384)への唯一の窓口
- 共有: `ensure_folder`(パス一致検証つき)、`add_peer`、
  `accept_pending(only=)`、`accept_pending_folder_offers`、
  `remove_device / device_folders`(キックと影響範囲)、
  `remove_folder`(不可逆)/ `pause_folder`(**可逆**。PATCHで `paused` のみ)
- 招待: `make_invite / parse_invite`(公開情報のみのJSON)
- 診断: `status_report()` がUIに出るすべての状態・問題文言を作る。
  `folder_detail()` が1フォルダ分の状態(state / need_bytes / need_items /
  files / errors / error_example)を取る。共有一覧を1プロジェクト1枠で
  見せるため、**稼働中のフォルダごとに呼ぶ**(停止中は省く)
- `write_stignore` / `STIGNORE_LINES`: 同期除外(board.html等)

**改造ポイント**
- 同期から外すファイルを増やす → `STIGNORE_LINES`(既存プロジェクトにも
  次回セットアップ時に自動追記される)
- パネルの問題診断の文言・条件 → `status_report()` 内。
  **他プロジェクトの共有を警告にしないのは意図的**(複数の現場に出入りする
  使い方では正常な状態であり、赤を乱発すると実害のある問題が埋もれる)
- 共有一覧の各枠に情報を足す → `status_report()` の `folders` に項目を追加し、
  必要なら `folder_detail()` で取得。表示は ui.py `_draw_folder_map`
- 招待ファイルに項目を足す → `make_invite` と `parse_invite` の両方
  (parse側は必ず検証・長さ制限を付ける)
- 既定ポート → `DEFAULT_GUI`(28384)。ユーザー上書きはプリファレンス側
- **注意**: ここに機能を足すときは「外部通信は github.com と 127.0.0.1
  のみ」の設計を壊さないこと(ALLOWED_HOSTS)

### board_html.py — 進捗ボードの静的HTML生成
- `export_board_html()`: `.musubi/board.html` をローカル生成(同期しない)
- `STATUS_COLORS`: 状態の色 / `_CSS`: 見た目全般
- 全ユーザー入力は `_esc()`(html.escape)必須

**改造ポイント**
- ボードの見た目 → `_CSS` と `STATUS_COLORS`
- 列の追加 → `export_board_html` のテーブル生成部(tasks.board() の行が
  持つキーはそのまま使える)+ヘッダー行
- **新しい文字列を埋め込むときは必ず `_esc()` を通す**(注入対策)

### security.py — 環境記録と監査
- `write_env / check_env`: `.musubi/env/env_<host>.json`
  (Blenderバージョン等の環境不一致検出)
- `audit()`: 監査の実行本体。チェック項目の追加はここ
  (autorun / 危険ファイル / 競合 / シンボリックリンク / 古いロック / env)
- `LEVEL_CRITICAL / WARN / OK`: 3段階(UIの赤/黄/緑に対応)

**改造ポイント**
- **監査項目を足す → `audit()` に `results.append((LEVEL_*, "文言"))` を
  返すチェック関数を1つ追加するだけ**。UI側は自動で色分け表示
- 環境チェックの比較対象を増やす(GPUドライバ等)→ `write_env` の
  記録キーと `check_env` の比較の両方

### quality.py — 品質チェックのロジック本体(bpy参照あり)
- データ層寄りだが、シーンの中身を見るため `bpy.data` を読む
  (書き込みや UI はしない。純データ層ではない例外)
- `LEVEL_OK / WARN / CRITICAL`: 3段階(security.py と同じ値。UIの緑/黄/赤)
- 各チェック関数 → `run_all()` が集約して `(level, 文言)` のリストを返す:
  1. `check_unapplied_scale`(スケールにキーが無いものだけ対象)
  2. `check_default_names`(`DEFAULT_NAME_RE` = Cube/Material.001 等)
  3. `check_images`(パック/リンク切れ/プロジェクト外)
  4. `check_orphans`(参照ゼロの孤立データ)
  5. `check_libraries`(リンク切れ/絶対パス/プロジェクト外)
- `record_deps()`: カットのリンク先を `.musubi/deps/sceneXX_cYY.json` に記録
- `asset_usage()`: 逆引き(このアセットはどのカットで使われているか)

**改造ポイント**
- **チェック項目を足す → 新しい `check_*()` を書いて `run_all()` に
  `results.append(...)` を1行追加**。UI(quality_ops.py の `draw_qc_box`)は
  レベルで自動色分けするので表示側の変更は不要。ただし「修正ボタン」が
  要るチェックなら quality_ops.py にオペレーターを追加する
- デフォルト名の判定を緩める/厳しくする → `DEFAULT_NAME_RE`
- 重大度を変える(警告→致命的など)→ 各 check 関数が返す `LEVEL_*`
  (赤=CRITICALはUIで alert 表示になる。乱発しない方針)
- **注意**: work/publish分離も自動修正もしない、が確定方針。
  チェックは気づかせるだけ、直すのは常に確認ボタン経由

## オペレーター層(bpy依存)

### ops.py — 保存・ロック・出力のライフサイクル中枢(最重要)
- `on_load_post`: 開いた瞬間のロック取得/警告/前ファイルのロック返却
- `on_save_post`: **Ctrl+S を「パイプライン保存」にしている本体**。
  バックグラウンド履歴退避(`_snapshot_bg`)、ロック、ステータス自動遷移
  (todo/retake→wip+担当自動設定)、依存記録、品質チェック
- `_THROTTLE_S = 600`: 無記入保存の履歴記録間隔(10分)
- `MUSUBI_OT_save_cut`(初回配置保存)、`MUSUBI_OT_render_output`
  (連番出力+ステータス→review)、`MUSUBI_OT_reload_libs`(リンク再読込)

**改造ポイント**
- 自動履歴の頻度 → `_THROTTLE_S`
- 保存時の自動処理を足す/外す → `on_save_post` の該当ブロック
  (ステータス遷移をやめる、通知を足す等はここ)
- 出力時の自動遷移(→レビュー待ち)を変える → `MUSUBI_OT_render_output`
- **注意3点**: ①ハンドラー内で保存をブロックすることはできない(advisory)
  ②ポップアップは `bpy.app.background` ガード必須(ヘッドレスで
  クラッシュする) ③保存を遅くする処理は必ずバックグラウンドスレッドへ
  (`_snap_lock` で直列化)

### st_ops.py — 同期のオペレーター群+プリファレンス
- 「次の一手」ナビの実処理(setup / invite export・import / accept /
  stop / remove_device / remove_folder)
- `maybe_auto_resume / autodetect_project / on_root_update`:
  開いただけで root・同期IDが埋まり同期が再開する仕組み
- `request_refresh()`: イベント駆動の状態取得(**常駐ポーリング禁止**の要)
- `MusubiAddonPreferences`: 役割スイッチ(制作者/レビュアー)とポート設定

**改造ポイント**
- プリファレンスに設定を足す → `MusubiAddonPreferences`(読み出しは
  `context.preferences.addons[__package__].preferences`)
- 状態表示の更新タイミングを増やす → `request_refresh()` を呼ぶ箇所を
  足す(タイマー常駐は不可)
- セットアップの流れを変える → `MUSUBI_OT_st_setup.execute`
  (ID自動決定 → ensure_config → start → ensure_folder → 招待書き出し)

### task_ops.py / review_ops.py / ver_ops.py / quality_ops.py / spec_ops.py
- それぞれ tasks / reviews / versions / quality / spec の
  「ボタンとリスト表示」。パターンは共通:
  `refresh_*(context)` がデータ層を読んで WindowManager の
  CollectionProperty に詰める → UIList が表示 → オペレーターが
  データ層を呼んで書き込み → refresh
- quality_ops.py `draw_qc_box` / spec_ops.py `draw_spec_box` は
  ui.py から呼ばれる描画部品(パネル本体はui.py)

**改造ポイント**
- ボードの行表示の書式 → task_ops.py `refresh_board`(1行のlabel生成)
- レビュー一覧の書式 → review_ops.py `refresh_reviews`
- 品質チェックの「修正ボタン」を足す → quality_ops.py にオペレーター追加
  +`draw_qc_box` にボタン(**自動修正は禁止。必ず確認ボタン式**が方針)

### reel.py — デイリーズリール
- `collect_clips`(各カットの最新出力を収集)→ `build_reel`
  (一時シーンのVSEで連結+カット名テロップ)→ 連番書き出し

**改造ポイント**
- リールにフレーム番号や日付を焼き込む → `build_reel` のテキスト
  ストリップ生成部
- 並び順・対象(承認済みのみ等)→ `collect_clips`
- **注意**: Blender 5.x では `sequence_editor.strips`、空コレクションが
  falsy になる罠がある(hasattrで書く)

### ui.py — パネル(描画専用)
- パネルの並び = `CLASSES` の順。親子は `bl_parent_id`
- `_is_reviewer()`: 役割スイッチ判定。レビュアーで隠すパネルは
  各クラスの `poll` に `return not _is_reviewer(context)`
- `_draw_st_nav`: 「次の一手」ボタンの出し分けロジック(状態→1ボタン)
- `_draw_folder_map`: 共有一覧。**1プロジェクト = 1つの `box()`**。
  状態は `_folder_dot()` が色付きドット1つに落とし、`_folder_summary()` が
  状態・進捗・相手を1行にまとめる。現在のプロジェクトを先頭に固定し、
  残りはID順(並びが毎回変わらないように)
- `_project_flavor`: 構成種別の自動判定(5秒キャッシュ)

**改造ポイント**
- パネルの順番・見出し・アイコン → `CLASSES` の順と各 `bl_label` /
  `draw_header`
- レビュアーで隠す範囲を変える → 各パネルの `poll`
- ナビの文言・条件 → `_draw_st_nav`
- 共有一覧の状態の色分け → `_folder_dot()`(判定は重い順)。
  文言は `_folder_summary()`
- **注意4点**: ①draw内でディスク/ネットワークI/O禁止(毎フレーム呼ばれる)
  ②アイコン名は5.xで廃止されたものがある(既存で使っている名前から選ぶ)
  ③赤(alert)はCRITICALのみ、注意は黄アイコン+通常文字が色方針
  ④**ラベルの文字色は自由に変えられない**。色を使いたいときは
  色付きアイコン(`COLLECTION_COLOR_01〜08`)を使う。
  `STRIP_COLOR_*` は 4.3 に存在しないので**使ってはいけない**
  (対応下限が 4.2 のため。4.3 と 5.1 で実機確認済み)

## 横断ルール(どこを触るときも)

1. **プロジェクト内への書き込み**は `safe_path` で検証し
   `atomic_replace`(または tmp→replace)で書く
2. **データ層に bpy を持ち込まない**(テスト可能性が壊れる)
3. **共有インデックスファイルを作らない**(1件=1ファイル+フォルダ走査)
4. **常駐処理を足さない**(タイマー/スレッドはイベント駆動・短命のみ)
5. **ルート外パスは PipelineError**(生の ValueError を漏らさない)
6. 文字列をHTMLに入れるときは `_esc`、外から読むJSONは形式検証+長さ制限
7. 新しい `.py` には SPDX ヘッダーを付ける(テストが検査している)
8. リリース時: \_\_init\_\_.py と manifest の**バージョン2箇所**、
   リリースノート(GitHub Releases)、ガイド該当箇所。zip は
   `blender --command extension build` で作る(pycache は
   `paths_exclude_pattern` が除外する)
9. テストはデータ層をシステムPythonで(`python -m pytest`)。
   UI表示だけの変更でも、実際にインストールして register が
   通ることを確認する
